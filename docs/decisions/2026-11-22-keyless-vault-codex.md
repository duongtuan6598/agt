1. **Derivation and the “keyless” claim.** No ordinary EVM address or Bitcoin NUMS key proves that nobody knows its private key: addresses are short hashes, and NUMS/Taproot security relies on discrete-log assumptions. For EVM, deploy a fixed, immutable `CREATE2` sink whose runtime has no successful call path and whose init/runtime hashes and salt are published. Verify its address, code, and deployment; this is an enforceable sink only on chains where code-bearing accounts cannot originate transactions and the sink cannot be replaced or cleared. A hash-derived EOA address alone is not proof. For Bitcoin, use an `OP_RETURN` output: consensus makes it unspendable, but it is **not a normal address or retained UTXO**. A NUMS Taproot output is easier to present as an address, but is not a proof of keylessness; also, omitting a script tree does not remove its key path. Thus the exact “address, provably keyless, visible balance forever” requirement cannot be met uniformly. Publish derivation parameters and per-chain verification tools, and state each chain’s guarantee honestly.

2. **Attribution.** Encode the destination agt-1 account in a canonical format (e.g. raw 20-byte account plus chain ID and version). For EVM native deposits, put it in transaction calldata sent with value to the sink; validators bind the calldata to that transaction’s value and sender. For ERC-20, don’t infer attribution from a standard `transfer`: it has no memo. Require a fixed, audited adapter that calls `transferFrom` directly to the sink and emits an attribution event; allowlist tokens and reject fee-on-transfer/rebasing behavior. For Bitcoin, put a tagged account payload in an `OP_RETURN` output; validators bind it to the transaction and deposited output. Missing or malformed attribution means **no mint**; define a recovery/expiry policy, never guess a recipient.

3. **Deposit verification.** Make deposits explicit agt-1 transactions carrying the source-chain transaction and inclusion proof. Validators verify against independently maintained source-chain headers/light-client state—not a single RPC—and check sink, amount, token, attribution, and confirmation/finality threshold. Bitcoin validators check proof of work, difficulty, and confirmations; EVM validators check finalized headers and receipt/log proofs. Track source chain + transaction/output/log index as a unique deposit ID; reject replays. Reorgs before threshold mean no credit; after credit, halt/resolve via a defined dispute or insurance rule—don’t silently mint twice. Each validator must independently verify proofs; RPCs are data relays, not authorities.

4. **Gold valuation.** Specify the gold unit, timestamp rule, and conversion formula. Use a quorum of independent, signed gold/fiat price feeds and a deterministic median over a fixed window; require a minimum quorum and bounded staleness/deviation. Validators verify signatures and calculate the same value. This reduces single-source risk; it does not eliminate oracle/provider and fiat-rate dependencies.

5. **Caretaker node and dependencies.** The founder’s node may relay proofs, run an indexer, and propose transactions. It cannot unilaterally make invalid deposits valid, override validator checks, reverse source-chain finality, or guarantee a price. Dependencies remain: source-chain consensus/finality, agt-1 validator participation, approved token behavior, oracle quorum, and any chain-specific sink assumptions.

6. **Mint cap.** Credit each verified deposit once, record its agreed gold value and resulting `vaultMinted` in consensus state, then apply the existing work-mint limits using integer, documented rounding: lifetime work mint ≤ `100 + floor(vaultMinted/19)` AGT; daily work mint ≤ `1 + floor(vaultMinted/3650)` AGT. Define `vaultMinted` as cumulative credited deposits, not current vault balance, so withdrawals, burns, or reorg handling cannot retroactively expand the cap.
