### D-1 [Critical] Locked milestones become unrefundable after the first delivery
Where: app.js:536-550, 577-579, 595-597 · Problem: `eng-open` locks every milestone up front, but `eng-cancel` is only allowed while `!e.started`; once any milestone is delivered, `e.started=true` and undelivered `pending` milestones cannot be cancelled. `eng-dispute` for a pending milestone requires `revisions >= MAX_REVISIONS`, which never happens if it was never delivered. · Scenario: client opens a 10-milestone contract; AI delivers milestone 1 then disappears. Milestones 2-10 are `pending`, client cannot cancel, cannot dispute, and escrow stays locked forever. · Fix: permit client refund/cancel of undelivered pending milestones after a per-milestone deadline, or lock milestones incrementally instead of all at open.

### D-2 [Critical] Drawn reviewers who never vote permanently strand disputes
Where: app.js:567-574, 933-948, 489 · Problem: contract disputes settle only when every reviewer votes; the timeout split runs only when `!x.reviewers`. Work jobs have no timeout at all. · Scenario: reviewers are drawn, one is offline/refuses/cannot pay after free quota, so `Object.keys(votes).length !== reviewers.length`. The milestone stays `disputed` and escrow stuck; the work job stays `drawn` and worker never paid. · Fix: add a vote deadline; settle from votes received, or split/refund, or redraw. Make reviewer voting free or escrow its fee.

### D-3 [Critical] Price reports are free and unlimited per block, enabling arbitrary Kho mint
Where: app.js:602-617, 630-632, 861-865 · Problem: `price-report` returns `0n` and never calls `signedBy`, so it has no fee/quota. Each report is only clamped ±10% from the *current* median, but a reporter can submit many sequential nonces in one block, moving the median arbitrarily. Kho credits then use the current price. · Scenario: at start the granter is sole price voice; it submits repeated +10% reports before a `kho-credit` tx in the same block (ProcessProposal does not enforce ordering or price), minting far more AGT than the deposit is worth. Even without reordering, proposer can delay a deposit until the price is favorable because valuation is at inclusion, not deposit block. · Fix: enforce one report per reporter per height/block and charge a fee; value Kho deposits at their block or a robust TWAP; ProcessProposal must verify valuation/order.

### D-4 [High] Licence and price authority revert to the founder after the threshold is crossed
Where: app.js:216-221, 195-203, 416 · Problem: `licAuthorised` and `priceReporterOk` test `licOwners(s).length < CARETAKER_UNTIL` against the *current* owner count. If active owners drop below 4, the granter again becomes sole licence authority and price reporter. The caretaker validator retirement is one-way, but this authority is not. · Scenario: 4 owners exist; 3 collude to revoke the 4th. Owners=3, so the founder regains unilateral grant/revoke and price reporting even though the caretaker validator is retired. · Fix: store a one-way flag when the threshold is first reached and never let the granter sign licence changes or price reports again.

### D-5 [High] Wages go to the old holder after revoke+regrant of the same agent
Where: app.js:676-688, 405-447, 884-898 · Problem: `bind` writes `s.cmt[cmtAddress] = {agent, holder, pubKey}` once. Licence revoke/grant updates `s.valset` but never updates `s.cmt`. If the same agent is revoked and re-granted to a new holder, `activeSet` uses the new holder via `s.valset`/`s.binds`, but `FinalizeBlock` still pays wages using the stale `s.cmt` holder. · Scenario: AI A bound under holder H1; H1 revoked; A re-granted to H2. A keeps signing, but wages for its blocks are paid to H1. · Fix: update `s.cmt` holder on licence activation/revocation, or resolve holder from current `s.valset` by agent when paying wages.

### D-6 [Medium] `/release` crashes on stale attestations from revoked validators
Where: app.js:1063-1067 · Problem: `/release` maps every stored attestation agent through the *current* `s.valset.validators`. If an agent attested while licensed and was later revoked, `ownerOf.get(agent)` is `undefined`; `.sort((a,b)=>BigInt(a.holder)<BigInt(b.holder)?-1:1)` then throws on `BigInt(undefined)`. · Scenario: withdrawal #n has an attestation from validator V; V is later revoked; querying `/release/n` throws instead of returning a valid package. · Fix: filter attestations to current validators or store the holder at attestation time; handle `undefined` before sorting.
